# Notice Exorcist: Devpost write-up

Every figure below is from this repo; the file that backs each claim is named next to it. All accuracy and duty results are in-sample: they come from the three bundled specimen notices and the bundled sample data (10 HTS chapters, 108 hand-picked CROSS rulings), and say nothing about other notices.

## Inspiration

Small importers and online sellers regularly receive customs notices that read like incantations: a Request for Information, a Notice of Action, a changed classification, a duty bill that does not match what they expected. The people receiving them are not trade lawyers or brokers; they run a shop. We wanted a tool that treats the notice as the monster under the bed, shows exactly what is in it, and hands back a calm, checkable answer. The Halloween angle gave us a way to make dry paperwork memorable without hiding the seriousness. We also wanted to show that a tool with a model in it can be trusted near money only if the model is never allowed to do the arithmetic.

## What it does

A user uploads a PDF, PNG or JPEG of a US customs notice (CBP Form 28, CBP Form 29 or a courier duty invoice), or forwards it to the app's inbound email endpoint. A local vision model (qwen2.5vl:7b through Ollama) reads the header fields and line items into Zod-validated JSON, and fields it may have misread are held for the user to confirm. With no model running, the app replays recorded model replies for the specimens, so it works with no key. Each printed HTS code is looked up in a local index of the USITC tariff schedule, and candidate codes and CBP CROSS rulings are found by full-text search over the goods description; they are shown as cited candidates, never as a classification. A deterministic duty engine recomputes every line duty and the MPF and HMF fees from the values printed on the notice, shows the formula, inputs and rounding for each, and flags where the notice and the recomputation disagree. Each line gets a short plain-English note; the wording is fixed text chosen by the engine's result (`apps/web/lib/explain.ts`), not written by a model. For a notice with a disagreeing line, the app builds a cited reply draft in code, placing figures and citations from provenance records. The user edits it and ticks an approval bound to the draft's sha256 hash; the server refuses to export anything else. Export is a PDF with the calculation trail and sources. Nothing is filed or sent automatically.

Measured accuracy (in-sample, `packages/notice-extract/eval/results/RESULTS.md`): 96.3% of fields read exactly right (234 of 243) across five inputs (the three specimen PDFs, a PNG and a phone photo of the Form 29), from 93.6% to 100% per input; all 9 of 9 wrong fields were flagged for the user to confirm.

## How we built it

We built it in Kiro from a spec-first workflow. The duty-calculator spec defines inputs, outputs, rounding rules and property-based invariants before any code existed. A TypeScript monorepo (Bun workspaces) holds a Next.js front end with its API routes, an extraction package that turns scans into typed JSON with a local vision model (an Amazon Bedrock path exists but is experimental and tested only with a mocked client), and a pure calculation package using decimal.js with no network, file or model access. A tariff-data package builds a SQLite FTS5 index from a committed snapshot of the USITC schedule and CROSS rulings; the web app reads that index directly. A custom MCP server, tariff-mcp, wraps tariff lookup, ruling search, rate parsing and the calculator for Kiro to use while building; the web app does not call it. Four Kiro hooks ask the agent to run the property tests or check a rule when certain files change; they advise, they do not block anything. Steering files encode the no-model-arithmetic rule, the spooky design language and the approval gate. The whole thing runs locally or in Docker (`docker run --rm -p 3000:3000 notice-exorcist`); there is no hosted deployment.

## Challenges

The hardest problem is trust. A model that reads a scan can misread a digit, and a model that explains a duty can invent a rate. We handled this by splitting responsibilities: the model only reads the document, and every money figure the API returns must carry a `stated`, `computed` or `tariff` provenance record and a source, or the response is refused with a 500 (`apps/web/lib/provenance-guard.ts`). Tariff schedules also have messy rate expressions (percentages, per-unit amounts, compound forms), so we scoped the parser to a grammar we can test and return everything else as `unsupported` rather than guessing (`packages/duty-engine/src/rate-text.prop.test.ts`). Confidence scores turned out not to be enough: 8 of the 9 wrong fields in the eval were read with confidence 0.95, above our 0.8 threshold, and were caught only by rule-based checks (for example, a courier invoice whose "importer" is the courier itself). Measured results on our test set: 96.3% exact (234 of 243 fields), 9 of 9 wrong fields flagged, in-sample only.

## Accomplishments

We are proud that the calculator is a standalone, model-free package with a written spec, property tests and a provenance trail, so a skeptical reader can verify any figure by hand. We are also proud of the interface: the notice becomes a haunted document where disagreeing lines glow and verified lines go quiet, and the exorcism flow walks the user through confirmation, review, editing and approval without a blank chat box. The `.kiro` folder holds the specs, hooks, steering and MCP config the project was built with. Test counts from a full run, all passing: 782 Vitest tests in 105 files, 95 Playwright e2e tests (with axe-core accessibility checks), 72 tariff-data tests, 19 script tests and 53 tariff-mcp tests. We did not measure line coverage.

## What we learned

Steering documents are most useful when they state prohibitions, not just preferences; a short file saying the model must never compute a figure shaped every later prompt. Hooks in this project are prompts to the agent, not gates: they made it routine to rerun the property tests after an engine edit, but nothing stops a change that skips them, so the real guarantees live in the test suite and the server-side checks. Specs forced us to write down rounding and edge cases early, which is exactly where money bugs hide. A custom MCP server let the IDE agent look up real tariff lines and compute duties with the real engine instead of doing the math itself; the product reads the same index through its own package. Concrete findings from the build: a model's own confidence missed 8 of 9 misreads, so cheap rule checks on the extracted JSON mattered more than the threshold; and parsing rate text into a small grammar with an explicit `unsupported` result was safer than trying to cover every form.

## What's next

After the hackathon we want to broaden the supported rate formats, add more notice types, and let customs brokers review and annotate drafts for their clients. A local-only mode already exists and is tested end to end (`e2e/local-mode.spec.ts` runs the specimen flow with outbound connections refused); next is an export of the full calculation trail for audits and the in-app notice for the cloud reading path. If this becomes a real business, we would validate the product with actual importers before charging anyone, and we would be explicit that the tool drafts and explains but does not replace a licensed customs broker. Customer discovery results: none yet; no importer outside the team has used it.

## How we used Kiro

- **Specs** (`.kiro/specs/`): one spec per feature (`duty-calculator`, `tariff-data`, `tariff-mcp`, `notice-extraction`, `specimen-notices`, `exorcism-flow`, `accessibility-edge-cases`), each with numbered EARS-style requirements, a design and a task list. Tasks name the test that covers them, and we implemented them one at a time so the specs stayed the source of truth. The duty-calculator spec defines rate types, half-up rounding to cents, MPF and HMF handling and invariants such as the total equals the sum of its lines and fees.
- **Hooks** (`.kiro/hooks/`): four file-edit hooks that ask the agent to check, not fix. `engine-property-tests` runs the duty-engine suite, including the fast-check property tests, after an edit under `packages/duty-engine/src`; `ui-money-literals` flags hard-coded currency or percent literals in `apps/web` components; `spec-task-has-test` checks that every ticked task names a test file that exists; `refresh-fixture-index` reruns the tariff-data tests when fixtures or tariff data change. They advise; they do not block saves or commits. Hook results during the build: we did not log how often each hook fired or what it caught, so we make no claim about that; `test/kiro-config.test.ts` checks every hook's shape and that its file patterns match real paths.
- **Steering** (`.kiro/steering/`): `product.md` (audience and what the app never does), `tech.md` (stack and rules such as Zod at the model boundary and decimal.js for money), `structure.md` (package boundaries), `no-model-math.md` (the model never computes, converts or rounds a figure; every displayed number carries provenance) and `approval-gate.md` (approval bound to the draft hash, export refused without it) are included in every session; `design-spooky.md` only for files under `apps/web`.
- **MCP** (`.kiro/settings/mcp.json`): registers tariff-mcp, our stdio server with four tools: `lookup_tariff`, `search_rulings`, `explain_rate` and `calculate_duty`. It is a development tool for Kiro: the agent used it to look up real schedule lines and compute line duties with the real engine instead of doing the math itself. The web app reads the same index directly and does not call it. `calculate_duty` always asks for approval; a test fails if it is auto-approved.
- **Vibe coding**: the haunted-document look, the fog and glow, and the exorcism screens were shaped conversationally against the design steering file and `design/DESIGN.md`. Anything that touches a number went through a spec instead.
